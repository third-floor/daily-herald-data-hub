# Daily Herald Data Hub

A static website, published with GitHub Pages, that brings together the AI-generated data about the Daily Herald photographic archive (Science Museum Group collection) and the interactive tools built to explore it. It also links to the related services hosted elsewhere.

The repository holds two things:

* **The source data:** the original exports, stored as JSON files of at most 20 MB.
* **The code:** it turns that data into the website and the files each tool reads.

The website itself is generated by GitHub Actions on every push and is never committed.

## Architecture at a glance

```
 Original exports (Google Drive)
   ├─ flat transcription JSON         data_1–4.json
   ├─ compact structured JSON (v6)    data_5–10.json
   └─ pipeline spreadsheet (xlsx)     visual elements + full v6 metadata
                │
                │  colab/01_initial_setup.ipynb  →  scripts/prepare_sources.py
                ▼
 data/source/                         ← committed to git
   <source>/part-0001.json …            each ≤ 20 MB, originals kept as exported
   manifest.json                        inputs, checksums, counts, renamed columns
   reports/                             duplicate uids that were replaced
                │
                │  GitHub Actions  →  scripts/build.py   (on every push)
                ▼
 _site/                               ← deployed to GitHub Pages, never committed
   index.html                           hub page
   tools/*.html                         seven widgets
   assets/hub-data.js                   shared data loader + loading screen
   data/manifest.json                   counts + list of every data file
   data/records/ …                      one combined record per photograph
   data/search/, data/search_extra/     text-search files
   data/widgets/<view>/ …               data shaped for each widget
   data/visual/ …                       compact bounding-box files
   data/lookups/<name>/ …               optional lookup tables (e.g. gazetteer)
```

There are three layers:

* **Source** is the faithful, versioned copy of the exports.
* **Build** is a deterministic transformation of the source.
* **Site** is static HTML/JS that reads the built files over HTTP.

No server or database is involved.

## Source layer — `data/source/`

The originals are grouped into **sources**. A source is one kind of export, defined by a name, a format and a list of input files:

| Source | Format | Contents | Records |
|---|---|---|---|
| `transcriptions_v1` | flat JSON | catalogue fields + `Transcribed_Text` (+ spatial prompt fields) | one per photograph |
| `metadata_v6` | compact JSON (`te`, `conf`, `rat` …) | text elements, people, places, dates, rights, editorial, processing metadata | one per photograph |
| `pipeline_xlsx` | spreadsheet | catalogue fields, the **full** v6 metadata (incl. `name_as_transcribed`, authority IDs, `dates_associated`) and the **visual-elements run** (bounding boxes, validation, cost/tokens) | one per photograph |
| *(optional)* `place_gazetteer`, `category_map` | spreadsheet sheets, `role: "lookup"` | place → coordinates, keyword → forecast category | lookup rows |

`prepare_sources.py` does the following for each source:

* **Splits by size, not record count.** It writes `part-0001.json`, `part-0002.json`, … and starts a new file before one would exceed 20 MB. Each file is a valid JSON array with **one record per line**, so git stores and compares it line by line.
* **Unwraps wrapped files.** It accepts bare JSON lists and wrapped objects such as `{"schema_version", "records": […]}`. The wrapper metadata is kept in the manifest.
* **Converts spreadsheets row by row:**
  * repeated column names are renamed rather than overwritten (`gem_model`, `gem_model__2`, …);
  * cells containing JSON are decoded into real JSON;
  * cells that look like JSON but are invalid, such as text truncated at Excel's cell limit, stay as text and are counted;
  * `None`, `nan` and empty cells become `null`.
* **Removes duplicate `uid`s within a source.** The record from the later input file wins, and replaced uids are listed in `reports/<source>_duplicates.csv`. For example, every photo in `data_5.json` also appears in `data_6.json`, and the `data_6.json` version is kept.
* **Drops excluded fields.** It removes fields matching the source's `drop_fields` patterns, e.g. `"output - *"` removes the old Gemini 2.5 Flash transcriptions from `transcriptions_v1`.
* **Adds provenance.** Each record gets `_src: {file, row}`. Nothing else in the record is changed; text repair happens later in the build.
* **Compares with the previous version.** Before overwriting, it reports how the source has changed: records before and after, how many were added or are no longer present, and any new or missing fields.

`data/source/manifest.json` records, for every source:
* its input files (size and SHA-256);
* the record count;
* the duplicates removed;
* the fields dropped;
* the schema detected for each record;
* the columns renamed and the JSON cells that couldn't be parsed;
* the list of chunk files.

It also records how the sources overlap by `uid`.

## Build layer — `scripts/build.py`

The build reads every source chunk and joins records on `uid` into **one record per photograph**.

**Recognising records.** Each record's layout is detected from its keys:

| Detected as | Recognised by | Becomes |
|---|---|---|
| `v1_flat_json` | `Transcribed_Text` / `output - …` keys | `transcription_v1` section |
| `v6_compact_json` | `te`, `date_info`, `places_dep` | `metadata_v6` section (keys expanded) |
| `pipeline_xlsx` | `gem_text_elements`, `gem_controlled_objects` | `metadata_v6` section (preferred) + `visual_elements` section |

**Merge rules:**
* **Catalogue fields** (identifier, title, description, date, maker, images) are taken from the first source that has them.
* **v6 metadata:** when a photograph has it in both the compact JSON and the spreadsheet, the **spreadsheet version is used**, because the compact JSON is an abridged export of it.
* **Transcription:** each photograph gets one top-level `transcription`, taken from the newest source that has one. That is the v6 text elements, otherwise the v1 `Transcribed_Text`.
* **Gemini 2.5:** the `output - gemini-2.5…` columns are never used.

**Transformations:**
* **Key expansion.** The compact v6 keys are renamed to the spreadsheet's full names, so both sources produce the same shape:

  | compact | full | compact | full |
  |---|---|---|---|
  | `te` | `text_elements` | `conf` | `confidence_score` |
  | `type` (text element) | `element_type` | `rat` | `rationale` |
  | `text` | `transcription` | `from` | `derived_from` |
  | `leg` | `legibility` | `cert` | `identification_certainty` |
  | `depicted` / `mentioned` | `people_depicted` / `people_mentioned` | `rel` | `relationship_label` |
  | `places_dep` / `places_men` | `places_depicted` / `places_mentioned` | `name` | `name_standardised` |
  | `date_info` | `date_primary` | `holder` | `copyright_holder` |
  | `activity` | `depicted_activity.description` | `type` (place / right) | `place_type` / `rights_type` |
  | `meta` | `processing` | | |

* **Separating the two spreadsheet runs.** The spreadsheet contains two pipeline runs side by side: the metadata run, then the visual-elements run, with repeated column names. Every column from `gem_status` onwards belongs to the visual-elements run (configurable in `VISUAL_RUN_MARKERS`), so the second `gem_model`, `gem_image_used`, token counts and so on are attributed correctly.
* **Text repair.** Mojibake such as `Â»` or `ÃƒÆ’Ã¢â‚¬Å¡…` is repaired to `»` with `ftfy`, in the built output only.
* **Unknown fields are kept.** Fields the build doesn't recognise, typically added by a newer export, are kept under `other_fields` in the matching section. They are included in the hidden-metadata search text.
* **Omitted columns.** `gem_raw_response` (truncated in the spreadsheet) and the `*_objects_flat` columns are left out of the built output. They remain in `data/source/`.

## The combined record

Each record in `data/records/part-*.json` has this shape:

```jsonc
{
  "uid": "co8798550",
  "identifier": "1983-5236/41317",
  "title": "A photographic print of Industry, Agriculture, …",
  "description": "A photographic print from the Daily Herald Archive folder: Industry » Agriculture » …",
  "catalogue_date": "1931-11-17",
  "maker": "London News Agency Photos Ltd.",
  "catalogue_url": "https://collection.sciencemuseumgroup.org.uk/objects/co8798550/…",
  "images": ["…__1001_.jpg", "…__1002_.jpg"],
  "thumbnail": "…", "thumbnail_large": "…",

  "transcription": { "text": "…", "from": "metadata_v6" },     // newest available
  "sections": ["metadata_v6", "visual_elements"],              // which sections are present

  "transcription_v1": { "transcribed_text", "text_length", "spatial_prompt", "spatial_regions", "other_fields" },

  "metadata_v6": {
    "from_source": "pipeline_xlsx" | "v6_compact_json",
    "text_elements":    [{ "element_type", "transcription", "legibility", "language" }],
    "photographers":    [{ "name_standardised", "name_as_transcribed", "entity_type", "authority_record_id",
                           "identification_certainty", "confidence_score", "rationale", "derived_from" }],
    "people_depicted": […], "people_mentioned": [… + "relationship_label"],
    "places_depicted": [… + "place_type"], "places_mentioned": […],
    "date_primary": { "date_as_transcribed", "date_standardised": [], "relationship_label", "confidence_score", "rationale" },
    "dates_associated": [], "depicted_activity": { "description" }, "subjects": [],
    "rights": [{ "copyright_holder", "rights_type", "confidence_score", "rationale" }],
    "editorial": { "publication_name", "story_or_series_title", "caption_reference_codes",
                   "image_sequence_number", "accession_number" },
    "flat": { … },  "processing": { "model", "processed_at", "total_tokens", … },  "other_fields": { … }
  },

  "visual_elements": {
    "controlled_objects": [{ "term", "detail", "box_2d": [y1, x1, y2, x2], "box_px", "confidence_score", "rationale" }],
    "other_objects": […], "dropped_objects": […],
    "status", "validation_level", "validation_notes",
    "image": { "image_width", "image_height", "sent_width", "sent_height" },
    "processing": { "image_used", "model", "thinking_level", "total_tokens", "estimated_cost_usd", "pipeline_version", … }
  },

  "provenance": [{ "source": "pipeline_xlsx", "schema": "pipeline_xlsx", "file": "….xlsx", "row": 2 }]
}
```

`box_2d` coordinates are in Gemini's normalised 0–1000 space, ordered `[y1, x1, y2, x2]`, and refer to the image named in `visual_elements.processing.image_used`, which is the front of the print.

## Published data files

All of these are generated into `_site/data/` and listed, with sizes and record counts, in `_site/data/manifest.json`.

| Folder | One entry per | Contents | File size target |
|---|---|---|---|
| `records/` | photograph | the combined record above | ≤ 20 MB |
| `search/` | photograph | card fields for text search: uid, identifier, title, description, makers (with the field each came from), date and date details, transcription, images, catalogue URL, structured groups (photographers, people, places, rights, editorial, visual elements), section summary, and the `records/` part number | ~5 MB, so a search can start on the first file |
| `search_extra/` | photograph | `deep` (all other text) and `rat` (all rationale text), fetched only when those search options are enabled | ~5 MB |
| `visual/` | photo with visual elements | uid, front image URL, image size, makers, years, validation level, detections (term, kind, detail, confidence, rationale, `box_2d`) | ≤ 20 MB |
| `widgets/compact_v6/` | photo with v6 metadata | the compact v6 JSON layout, as in `data_5–10.json`, including metadata that came from the spreadsheet | ≤ 20 MB |
| `widgets/v1/` | photo with a v1 transcription | the flat transcription layout, as in `data_1–4.json`, without the Gemini 2.5 output | ≤ 20 MB |
| `widgets/dates/` | dated photo | spreadsheet-style row: `uid, identifier, title, description, date, maker, url, image_links, gem_date_flat, date_relationship, activity_description, gem_places_depicted, gem_places_mentioned, gem_maker_flat` | ≤ 20 MB |
| `widgets/visual_table/` | photo with visual elements | pipeline-spreadsheet row with catalogue fields, `gem_controlled_objects / gem_other_objects / gem_dropped_objects`, `gem_status`, `gem_validation_*`, image size, and all `gem_*` processing fields **from the visual-elements run** | ≤ 20 MB |
| `lookups/<name>/` | lookup row | lookup sources passed through unchanged (e.g. `place_gazetteer`, `category_map`) | ≤ 20 MB |

`manifest.json` also carries:
* the number of photographs and the per-section counts (`transcription`, `transcription_v1`, `metadata_v6`, `visual_elements`);
* photographs per decade;
* the 40 most frequent visual-element terms;
* the source list;
* build statistics.

## How pages load data — `site/assets/hub-data.js`

Every widget includes this script in its `<head>`. It provides:

* **`HubData.manifest()`** fetches `data/manifest.json` once and caches it.
* **`HubData.loadView(name)`** looks up `name` in the manifest (`widgets/<name>`, `lookups/<name>` or a top-level folder), fetches all of its part files in parallel (four at a time), and returns one combined array.
* **`HubData.load(view, ingest, options)` / `HubData.autoload(…)`** show a full-screen loading screen with a progress bar, load the view plus any `extra` / `optionalExtra` views, and pass the rows to the widget's own loading function (`ingest`).
* **The loading screen covers the page from the first paint.** The script hides the page body as soon as it runs, so the widget's own "drop a file here" screen is never shown while hub data is loading.
* **Fallback.** If the data can't be fetched, or the page is opened from disk (`file://`), the loading screen is removed and the widget's original upload screen is shown, with a short explanation.
* **"← Data Hub" link.** It also adds a small link back to the hub page.

The widgets' analysis code is unchanged. Each widget's existing "read a file" path was split into "parse the file" and "use these rows", and `hub-data.js` calls the second half directly.

## The hub page

`site/index.html` reads `data/manifest.json` and shows:

* **Headline counts:** photographs, transcriptions, structured records and visual-element records.
* **Search & play:** links to the external services.
* **Datasets:** one card per section with its count and description, plus download links to every `records/` part. It also links to `data/source/` in the repository; the address is worked out from the Pages URL.
* **Explore & visualise:** one card per widget.
* **Collection at a glance:** photographs per decade and the most frequent visual-element terms.

The lists of links and widgets are plain JavaScript arrays at the top of the page's script (`SEARCH_TOOLS`, `WIDGETS`, `SECTIONS`).

### AI Transcription Dashboard — `data_hub.html`
**What it does:** an archive-wide quality and content dashboard for the transcription and metadata work. Its tabs are:
* Overview
* Dates
* Catalogue ↔ AI comparison
* Photographers (with person/agency standardisation)
* People
* Entities
* Locations
* Text
* Legibility
* Duplicates (processing instances sharing a uid)
* QA
* Human review (decisions stored in the browser's local storage)
* Records

Global filters cover schema, source file, photographer, person, decade, date relationship, catalogue/generated date, legibility, element type and duplicate state.

**Fields it reads:**
* **From `v1`:** `uid, identifier, title, description, date, maker, Transcribed_Text, _src`.
* **From `compact_v6`:**
  * `id, uid, title, url, date`;
  * `date_info` (`date_standardised`, `relationship_label`, `confidence_score`);
  * `te` (`type, text, leg`);
  * `photographers, depicted, mentioned` (names);
  * `places_dep, places_men`;
  * `editorial.accession_number`;
  * `meta` (`model, processed_at, finish_reason, parse_error, total_tokens`);
  * `_src` (shown as the "Source JSON" filter).

### Photograph Archive Explorer — `data_vis_explorer.html`
**What it does:**
* A catalogue browser with subject filters and full-text search.
* A record detail view with images and transcribed text elements.
* An entity network linking photographs through shared photographers, people, places and subjects.

**Fields it reads:**
* `id, uid, title, imgs, url, date, date_info, activity`;
* `te`;
* `photographers, depicted, mentioned`, each with `name, conf, rat, cert, rel, from`;
* `places_dep, places_men`;
* `subjects` (`term, vocab`);
* `rights`;
* `editorial`.

### Textual Analysis — `linguistic_analysis.html`
**What it does:** analyses the language on photograph backs. Its tabs are:
* Typology of text elements (by type, words per type, over time, publications)
* Common words
* Keyword-in-context search
* Word associations
* Language over time
* Photographers
* People, places & subjects
* Records

It also finds gaps in the catalogue. You can add further datasets, as JSON files, to compare against the hub's.

**Fields it reads:**
* `te` (`type, text, leg`), `activity`, `date_info`;
* `photographers, depicted, mentioned, places_dep, places_men, subjects`;
* `rights, editorial, meta, imgs`;

### Date Explorer — `on_this_day.html`
**What it does:** shows when the photographs were taken or published, in three views:
* a month calendar for a specific year;
* an "On this day" calendar combining every year;
* collection statistics.

Images are not loaded; catalogue and image links are provided instead.

**Fields it reads:** `gem_date_flat` (the AI-standardised date), falling back to `date` (the catalogue date); `identifier, title, description, url, image_links`. Only rows with a complete day/month/year are placed on the calendar.

### Archive Weather — `archive_weather_forecast.html`
**What it does:** a playful TV-style "forecast" of the themes and places most active in the archive for a chosen date and the following week. It groups historic records by month and day, ignoring the year.
* **Themes:** assigned in the browser by keyword rules, or by the `category_map` lookup when present.
* **Location map:** shows places when coordinates are available from the `place_gazetteer` lookup. Without it, the map shows "No mappable locations yet" and the rest of the forecast still works.

**Fields it reads:**
* **Dates:** `uid, identifier, title, description, gem_date_flat`, falling back to `date`.
* **Content:** `activity_description, gem_places_depicted, gem_places_mentioned, url, image_links`.
* **Gazetteer** (when present): `raw_place, normalized_place, display_place, region, country, latitude, longitude`.
* **Category map** (when present): `match_type, match_value, primary_category, secondary_category`.

### Visual Elements Workbench — `visual_elements_workbench.html`
**What it does:** analyses the objects detected on the front of each print. Its tabs are:
* Overview
* Vocabulary
* People & Time
* Composition (orientation, box geometry)
* Text ↔ Image (detected objects against the transcription)
* Pipeline QA (validation, duplicates, cost, tokens, versions)
* Records

It has a search/filter bar (term, maker, decade, archive folder, orientation, validation) and a "Compare groups" mode. A second run can be loaded by hand as file B to compare runs.

**Fields it reads:**
* **Catalogue:** `uid, identifier, title, url, image_links`, `description` (parsed into the archive folder path), `maker, date`.
* **AI metadata:** `gem_maker_flat, gem_date_flat, gem_transcription_flat`.
* **Detections:** `gem_controlled_objects, gem_other_objects` (`term, detail, box_2d, confidence_score, rationale`), `gem_dropped_objects`.
* **Validation:** `gem_status, gem_validation_level, gem_validation_notes`, `gem_image_width/height`.
* **Image used:** `gem_image_used`.
* **Processing:** `gem_model, gem_thinking_level, gem_finish_reason, gem_error, gem_processed_at, gem_duration_seconds, gem_total_tokens, gem_input_total_tokens, gem_output_tokens, gem_thoughts_tokens, gem_estimated_cost_usd, gem_attempts`, and the `gem_*_version` fields.

### Spatial Explorer — `spatial_hover_explorer.html`
**What it does:** shows where in the frame each visual element tends to appear.
* **Hovering** over a normalised 0–1000 photo frame lists the five elements whose bounding boxes most often cover that point, ranked by photographs or by detections.
* **For each element** it shows confidence, observed details, common makers, years and example records. The example records can be opened with their box drawn on the image.
* **Dominant-element map:** an optional map colours the frame by the most common element in each cell.

**Fields it reads:** `uid, identifier, title, url, image_links, gem_image_used`; `gem_controlled_objects, gem_other_objects` (`term, box_2d, confidence_score, detail, rationale`); `gem_maker_flat` (falling back to `maker`); `gem_date_flat` (falling back to `date`).

**Why `visual_table` uses the visual run's values:** this widget and the Workbench match `gem_image_used` against `image_links` to find the image the boxes belong to. In the raw spreadsheet that column appears twice, and a plain spreadsheet reader returns the metadata run's value, which is the back of the print. `widgets/visual_table` supplies the visual-elements run's value, so the boxes are drawn on the correct image.

## Deployment

`.github/workflows/deploy.yml` runs on every push to `main` and on manual dispatch (**Actions → Build and deploy hub → Run workflow**). It runs these steps:

1. Check out the repository.
2. Set up Python 3.12.
3. Install `requirements.txt`.
4. Run `python scripts/build.py --source data/source --out _site --site site`.
5. Fail if any generated file exceeds 20 MB.
6. Upload `_site/` as a Pages artifact.
7. Deploy it to GitHub Pages.

The Pages source for the repository is set to **GitHub Actions**, so `_site/` never appears in the git history.

Third-party libraries are loaded from CDNs at fixed versions:
* SheetJS `xlsx@0.18.5`
* Chart.js `4.4.4`
* Leaflet `1.9.4` with `leaflet.heat@0.2.0`

## Design decisions and limits

* **JSON chunks instead of one file per record or a search index.** This keeps the repository to a few dozen data files (Pagefind would create thousands) while staying within GitHub's limits:
  * 100 MB per file (here, at most 20 MB);
  * a recommended repository size of about 1 GB;
  * 1 GB per published Pages site.
* **Only `data/source/` is versioned.** Rebuilding the published data doesn't add to the git history; only real changes to the source data do. Git LFS isn't used because GitHub Pages doesn't serve LFS files.
* **The source layer stays faithful; the build does the cleaning.** Text repair, key expansion and run separation can be changed and re-run without touching the originals.
* **Each widget gets a view in the layout it was written for.** The widgets stay independent single-file tools, still able to load a file by hand, and a change in one widget's needs only affects its own view in `build.py`.
* **Repeated data is a deliberate trade-off.** The same information appears in several published views (records, search, widget views). That costs Pages space in exchange for small, fast downloads per tool, and it doesn't affect the repository's size.
